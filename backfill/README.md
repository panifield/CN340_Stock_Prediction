# backfill/ — log ทำนายย้อนหลังของวันที่ระบบอัตโนมัติพลาด (ตั้งแต่ 2026-09-28)

**ไม่ใช่ log จริง** — ทุกแถวในโฟลเดอร์นี้ทำนายย้อนหลังหลังรู้ผลแล้ว (`generated_at` = เวลาที่รัน backfill
ไม่ใช่เวลาของวันนั้น) และมีคอลัมน์ `is_backfill=True` ติดทุกแถว **ห้ามนำไปปนกับ `task_*/results/prediction_log*.csv`**
ถ้างานนี้ต้องใช้หลักฐานว่าทำนายสดตามเวลาจริง ให้ใช้ log จริงเท่านั้น

ไม่ได้แก้ไฟล์ใดใน `task_*/` และ `automation/` เลย (เพิ่มเฉพาะโฟลเดอร์ `backfill/`)

## วิธีทำงาน
สคริปต์ [run_one.py](run_one.py) "ครอบ" ฟังก์ชันดึงข้อมูลของสคริปต์ predict จริงของแต่ละ task ให้ตัดข้อมูลไว้ ณ
เวลาตัดของวันนั้น แล้วเรียก `predict_one_ticker()` ตัวเดิม (โมเดล/feature/พารามิเตอร์ชุดเดียวกับระบบจริง ณ code_commit ที่บันทึกไว้)

| กลุ่ม | ข้อมูลที่ให้โมเดลเห็น | ข้าม guard อะไร |
|---|---|---|
| next_day (task_a, task_c) | ราคาปิดรายวันก่อนวัน target เท่านั้น | guard ตลาดปิด 10:00-18:00 |
| next_day (task_b) | `raw_data` สำเนา + ข้อมูล Yahoo ถึงวันก่อน target ตัดด้วย `--as-of` ของ task_b เอง | `--as-of` ปกติใช้ได้เฉพาะ dry-run, clean-tree |
| t1600 (task_a2, task_c) | แท่ง 1h ถึง 15:00 ของวัน target (ตัดแท่ง 16:00+ และวันหลังจากนั้น) | guard 16:00-16:30 |
| t1600 (task_b) | Yahoo 1h ล่าสุด รวมกับไฟล์ล็อกตามกติกาเดิมของ task_b | บังคับให้ snapshot ดาวน์โหลดวันเดียวกัน ≥16:00 |

ข้อมูลที่ดึงจาก Yahoo ทุกครั้งถูกเก็บแคชใน `data/yf_cache/` (ทุก run ใช้ชุดเดียวกัน, รายการใน `index.jsonl`)
ข้อมูลรายวันของ task_b ที่ต่อให้ทันอยู่ใน `data/task_b_raw_data/` (ผ่านการตรวจ OHLC ทับของเดิมเป๊ะแบบเดียวกับ
`tools/fetch_yahoo_daily.py`) และ snapshot 1h ของ task_b อยู่ใน `data/task_b_1h_snapshots/`

## ไฟล์
- `results/<task>_<mode>.csv` — ผล backfill (schema = log จริงของ task นั้น + `is_backfill`, `backfill_reason`; task_b t1600 มี
  `snapshot_path`, `locked_mismatch_bars`, `historical_x_match` เพิ่ม)
  - `backfill_reason`: `missing` = log จริงไม่มีวันนั้นเลย · `partial_models` = log จริงมีแค่ 1 โมเดล/หุ้น (ก่อนเปลี่ยนเป็น 3 โมเดล) backfill เติมครบ 3 โมเดล
- [COVERAGE.md](COVERAGE.md) / `coverage.csv` — ตารางว่าแต่ละวัน/แต่ละชุดมี log จริง, backfill หรือยังขาด
- `validation/` — ผลรัน backfill ในวันที่มี log จริงอยู่แล้ว (เพื่อวัดว่าตรงกับของจริงแค่ไหน) + `validation_vs_live.csv`
- `logs/` — stdout ของทุก run

## ความแม่นยำเทียบกับ log จริง (ผลจาก validation/)
รัน backfill กับวันที่มี log จริง แล้วเทียบ ([validate_vs_live.py](validate_vs_live.py)):

| ชุด | วันที่ทดสอบ | ผล |
|---|---|---|
| task_b next_day | 2026-10-06 | **เหมือนกันเป๊ะ** (ต่าง 0) ทั้ง 6 แถว |
| task_a next_day | 2026-10-06 | ต่างได้ ≤0.043 ใน P(พลิก) · label ตรง 5/6 |
| task_c next_day | 2026-10-06 | ต่างได้ ≤0.081 ใน P(ขึ้น) · label ตรง 6/6 |
| task_b t1600 | 2026-10-05 | ต่างได้ ≤0.0006 ใน predicted_return |
| task_a2 t1600 | 2026-10-06 | ต่างได้ ≤0.23 · **label ตรงแค่ 1/6** |
| task_c t1600 | 2026-10-05 | ต่างได้ ≤0.73 · label ตรง 4/6 |

สาเหตุที่ต่าง (ยืนยันแล้วว่าไม่ใช่ความสุ่ม — รันซ้ำบนเครื่องนี้ได้ค่าเดิมเป๊ะ):
1. **t1600: แท่ง 15:00 ที่เห็นตอน 16:02 ไม่เท่ากับแท่งสุดท้ายที่ Yahoo เก็บไว้ทีหลัง** เช่น 6 ต.ค. task_a2 สดเห็น
   KBANK 235 / ADVANC 341 แต่ backfill ได้ 234 / 340 (ต่าง 1 tick พอจะพลิก parity) task_b ตรวจเรื่องนี้ไว้เองแล้วใน
   `availability_1600.csv` (`bar15_changed_vs_later`) ใช้ข้อมูลชุดอื่นทดแทนไม่ได้ ดังนั้น **t1600 backfill เป็นค่าประมาณ ไม่ใช่การจำลองของจริง**
2. **next_day (task_a/task_c): ประวัติราคาที่ Yahoo คืนตอนนี้ไม่เท่ากับตอนนั้น** (log จริง 6 ต.ค. `train_rows`=2461
   แต่ backfill ได้ 2454 ที่ data_cutoff เดียวกัน — Yahoo เพิ่ม/ลบแถวย้อนหลังได้) task_b ไม่เจอปัญหานี้เพราะใช้ `raw_data`
   ที่ตรวจเทียบทุกวัน
3. เครื่อง/ไลบรารีที่รันต่างกัน (log จริงรันจากอีกเครื่อง) อาจทำให้ ANN/XGBoost ต่างเล็กน้อย

## วิธีรันใหม่ / เติมเพิ่ม
ต้องใช้ Python ของ `.venv` ของโปรเจกต์ (ติดตั้ง `lightgbm==4.7.0` และ `matplotlib==3.11.0` เพิ่มลงใน `.venv` แล้ว
ตาม `requirements.txt` — เวอร์ชัน numpy/pandas/scikit-learn/xgboost ตรง pin ของ task_b)

```powershell
.venv\Scripts\python.exe backfill\run_all.py --dry-plan   # ดูว่าจะเติมอะไร
.venv\Scripts\python.exe backfill\run_all.py              # เติมช่องว่างที่ยังไม่ได้ทำ (รันซ้ำได้ ข้ามที่ทำแล้ว)
.venv\Scripts\python.exe backfill\coverage.py             # สร้างตารางสรุปใหม่
```
ช่องว่างคำนวณอัตโนมัติจาก log จริง + ปฏิทินวันหยุดของ task_b (`set_holidays.txt`) จึงใช้เติมช่องว่างที่เกิดใหม่ในอนาคตได้ด้วย
(ข้อมูลของวันหลังสุดต้องนิ่งแล้วใน Yahoo)

## ทดสอบ data leak ([leak_test.py](leak_test.py))
คัดลอกข้อมูลที่แคชไว้แล้ว "วางยา" (ราคา ×1.5, volume ×5) แล้วรัน backfill ใหม่แบบออฟไลน์ ผลอยู่ใน `leak_test/leak_test_report.csv`
(ทดสอบ target 2026-09-29 และ 2026-10-07 ครบทั้ง 6 ชุด)
- **future** — วางยาเฉพาะข้อมูลที่ไม่ควรเห็น (next_day: ตั้งแต่วัน target ขึ้นไป · t1600: แท่ง 16:00 ของวัน target และทุกอย่างหลังจากนั้น)
  -> คำทำนายต้องเหมือนเดิมเป๊ะ: **ผ่านทั้ง 12/12** (ต่าง 0.000000)
- **control** — วางยาข้อมูลที่ควรเห็น (วันทำการก่อน target / แท่ง 15:00) -> ผลต้องเปลี่ยน: **เปลี่ยนทั้ง 12/12** (ยืนยันว่าการวางยาไวพอ)

ข้อควรระวัง: แท่ง 15:00 ถือเป็นข้อมูลที่ "ควรเห็น" เพราะครอบคลุม 15:00-16:00 และราคาปิดทางการเกิดหลังจากนั้น (~16:35)
แต่แท่ง 15:00 ฉบับสุดท้ายต่างจากที่เห็นตอน 16:02 ได้ ±1 tick (ดูหัวข้อความแม่นยำด้านบน) — เทียบ 12 ตัวอย่าง (task_a2 ที่มี log จริง)
ต่างกัน 5 ครั้ง ฉบับสุดท้ายไม่ได้ใกล้ราคาปิดมากกว่าอย่างเป็นระบบ (ค่าเฉลี่ย |ต่างจากราคาปิด| 0.75 vs 0.83 tick) จึงไม่พบหลักฐานว่าแอบเห็นราคาปิด
แต่ตัวอย่างน้อยเกินกว่าจะยืนยันเด็ดขาด
